# ADR-0162: Cloud Tasks implementation precedes final performance acceptance

- Status: Accepted
- Date: 2026-09-06
- Updated: 2026-09-19 (calibration preregistration and evidence pipeline for #1246)
- Updated: 2026-09-21 (execution moves wholly to a lean single-VM rig; deployed-failure validation is #1362's, corrected by [#1444](https://github.com/flink-gcp/flink-connector-gcp/issues/1444))
- Updated: 2026-09-23 (the rig's controller core is tracked and tested, and a run that outlives its reservation is recorded failed, revised by [#1457](https://github.com/flink-gcp/flink-connector-gcp/issues/1457))
- Updated: 2026-09-23 (a run's evidence lives inside its directory, and an offline analyzer applies the rule to the rig's runs, revised by [#1458](https://github.com/flink-gcp/flink-connector-gcp/issues/1458))
- Updated: 2026-09-23 (the preregistration is revised for the VM rig: the window is kept and instrumented, recovery is reported from single-host cells, and the cost ceilings exist, revised by [#1448](https://github.com/flink-gcp/flink-connector-gcp/issues/1448))

- Supersedes: only the Cloud Tasks requirement in [ADR-0104](0104-exactly-once-modes-use-service-native-replay-protection-and-pass-a-performance-gate.md) and [ADR-0158](0158-cloud-tasks-checkpointed-creation-stages-named-tasks-and-commits-after-the-checkpoint.md) for a separate primitive performance pass before implementation, connector-level evaluation or release

- Current behavior: `docs/content/docs/connectors/delivery-guarantees.md` § Performance decision rule

## Context

ADR-0158 defines checkpointed task creation, including random identities when the application cannot provide a stable key.
Its implementation-start condition required a primitive performance pass that the [#1241 repeat](evidence/0104-cloudtasks-stage1-1241.md#result-on-2026-09-06) did not supply.

## Evidence

The repeat's three completed one-channel measurements on 2026-09-06 observed no material named-task throughput decrease in the executed, capped cells: random names achieved 350.26 calls/s, hash names 358.45 calls/s, and unnamed tasks 335.83 calls/s, with 50,000 calls in each measured arm.
They ran sequentially in that order on an accumulating queue, at estimated starting depths of 202,740, 257,740 and 312,740; queue depth and arm order were not independently controlled.
The experiment nevertheless remains inconclusive under its preregistered rules: required repetitions and controls were missing, and the admission limiter waited after the initial in-flight window.
That verdict is not a measured failure of the throughput threshold.

The [post-run calibration](evidence/0104-cloudtasks-stage1-1241.md#post-run-local-calibration-2026-09-06) isolated a local pacing limitation and checked a repaired waiting implementation without a service client or network requests.
It does not establish the cause of the real run's multi-second response latency or estimate uncapped service capacity.
The concurrent replay's two successful same-name responses remain documented; the local validator's stop is not a service error code or proof of two persisted tasks.

## Decision

The owner [accepted implementation with these measurement limits](https://github.com/flink-gcp/flink-connector-gcp/issues/1238#issuecomment-5559502662).
Another standalone primitive repeat has less immediate decision value than implementing the accepted protocol and evaluating its complete cost.
This is a change to when performance acceptance is required, with the risk of implementation effort that the final assessment may decline.

The Cloud Tasks implementation may proceed from the accepted ADR-0158 protocol without a separate Stage 1 pass.
[#1241](https://github.com/flink-gcp/flink-connector-gcp/issues/1241) is complete as an inconclusive investigation; neither implementation nor release requires reopening it or relabeling its result.
The delivery order is:

| Work | Entry condition and responsibility |
|---|---|
| [#1242](https://github.com/flink-gcp/flink-connector-gcp/issues/1242) | Implement the accepted writer, immutable envelope and versioned committable format, with their deterministic tests. |
| [#1243](https://github.com/flink-gcp/flink-connector-gcp/issues/1243), then [#1244](https://github.com/flink-gcp/flink-connector-gcp/issues/1244) | Follow the merged predecessor with the committer/DataStream entry point, then Table integration and operational guidance. |
| [#1245](https://github.com/flink-gcp/flink-connector-gcp/issues/1245) | After integration, validate real-service recovery within ADR-0158's scope and the published service assumptions of ADR-0154. |
| [#1246](https://github.com/flink-gcp/flink-connector-gcp/issues/1246) | After the implementation tests and #1245 acceptance, evaluate the implemented mode and decide its supported workloads and release disposition. |

Implementation PRs may be reviewed and merged in that order before final performance acceptance.
The mode's release and any claim that it is supported require the correctness tests on both supported Flink lines, #1245 acceptance, and #1246's final assessment.
Development documentation that accompanies an API entry point states this remaining release condition.

The final assessment compares unnamed at-least-once, random/hash-named at-least-once, and staged creation with equivalent name distributions.
It reports both the total cost against the unnamed path and the incremental staging/commit cost against the named path, so accepting implementation does not discard the task-identity question.
The support thresholds apply to total staged cost against the unnamed path; the named baseline isolates the additional staging/commit cost.
It retains ADR-0104's general thresholds (at least 70% throughput and at most 2x p95), constrained thresholds (at least 25% and at most 4x), three measured repetitions after warm-up, and greater-than-10% variability rule.
The owner reduced the benchmark on 2026-09-23 to what answers whether staged creation keeps up with the unnamed path: equal conditions across arms still hold, and the assessment measures Flink 2.2.1, 1 KiB tasks, evenly distributed names, the `UNNAMED`, `NAMED_HASH` and `STAGED_HASH` arms, and three shapes — parallelism and concurrency 1/1, 4/4 and 16/16 with checkpoint intervals of 1, 10 and 60 seconds — at fixed rates, three repetitions each.
A support claim reaches only the shapes and rates measured; 64 KiB tasks, skew, the random-name arms, Flink 1.20.4 and a capacity above the measured rates are unmeasured, and supporting them takes a measurement of its own.
Duplicate-task replay is a separate workload; a repeated ID must not represent distinct accepted records merely to manufacture a hot key.
The reduced assessment measures throughput and task visibility latency; the other quantities #1246 lists are not measured by it.
An inconclusive final assessment supplies no support or release approval; a changed threshold or supported workload requires an explicit decision rather than retrospective reinterpretation.

Before any later service measurement, preregister its offered-load or capacity question and the evidence needed to answer it, calibrate the harness on the execution host, and include a sensitivity control that can detect a known regression.
The local wait repair alone does not validate a future capacity experiment: a deliberate pacing cap still limits what its throughput can establish.
Each real-GCP run retains separate approval of concrete resources, location, lifetime, operation/dispatch caps and cost, followed by verified cleanup.
The [calibration preregistration](evidence/0162-cloudtasks-assessment-1246.md) fixes the execution conditions, the calibration cells and their numeric ceilings, the instrument's acceptance criteria and the protocol interpretations the owner confirms before a session; the pinned protocol, the observation and reconciliation code and the offline analyzer are part of the reviewed supervisor bundle.
That paragraph describes the cluster, and the [2026-09-21 refinement](#execution-moves-to-a-lean-single-vm-rig-2026-09-21) moves this assessment off it entirely: on the VM rig the supervisor bundle, the session ledger and the receipt contract have no counterpart, and the preregistration's execution conditions, numeric ceilings, acceptance items and scale estimate are revised to name the rig covering each, by the preregistration's 2026-09-23 revision ([#1448](https://github.com/flink-gcp/flink-connector-gcp/issues/1448)).

## Execution moves to a lean single-VM rig (2026-09-21)

The owner decided on 2026-09-21 to take this assessment onto a lean single-VM rig, and confirmed the same day, on the evidence below, that it keeps no half on the cluster.
The quantities the assessment measures, its arms, cells, repetitions, periods, thresholds and variability rule are unchanged, and so is what it must answer. What changes is where the assessment executes and, following from that, its evidence contract and the instrument acceptance items, which are revised rather than reinterpreted. That is a refinement of how the evidence is produced, not of what counts as passing.

The reason is the third calibration rather than a preference. Run `cal1246c-221-1` met every rate it offered but its own delay control's — 100.0 % at 10, 25, 100, 1,000 and 2,000 records per second — and still failed four of six acceptance items, every one of them on the instrument or the environment: a delay control invalid by its own arithmetic, two cells whose JobManager Pod was replaced mid-measurement with no reason recorded, and a metric listing frozen empty on all ten cells.
Kubernetes is where Flink really runs; it is not a measurement instrument, and a campaign of 420 preregistered cells and 260 probes across at least 48 sessions would measure the environment's variance at that loss rate.

- The assessment — throughput, task visibility latency, the capacity search, and the staged-against-unnamed and staged-against-named cost comparisons — is to run on one `e2-standard-8` in `us-central1`, with a Compute Engine maximum run duration and `DELETE` termination action as the host deadline, on the operating model [ADR-0166](0166-bigtable-implementation-precedes-final-stage2-acceptance.md)'s refinement records: a single host under that deadline, a controller whose host-specific part stays outside tracked source, and a campaign of preregistered runs it sequences. How the frozen classpath reaches that host and the embedded cluster the runs use are the rig's own to record when it exists, and the controller's fork-per-run core is recorded below; this refinement does not borrow them from another ADR that does not carry them.
  The size is measured rather than copied. At 2,000 records per second and parallelism 16, `k06` of that run filled 7.51 GB of the 7.78 GB heap Flink derived inside a 16 GiB, four-vCPU TaskManager, while its JVM process-load samples peaked at 0.55 of those four vCPUs and usually sat below 0.30; memory is what binds. #1327 measured the same constraint from the other side on a 16 GB `e2-standard-4`: heap exhaustion in calibration forced its staged capacity down to 192 MiB per subtask, the most its parallelism-16 cells admitted inside a 10 GiB heap, and at that cap 129 of the 162 staged runs attempted at 64 KiB were censored for capacity against 27 of 162 at 1 KiB.
  Two limits of that evidence are worth stating: the load figure is the maximum of 33 samples about 19 seconds apart, so it bounds no instant between them, and `k06` is one of the cells this document counts as restarted — which makes it unusable as a throughput measurement but leaves its heap and load readings as what the shape actually asked of a machine.
- **This assessment has no cluster half**, and deployed failure is outside it on three counts. The pinned protocol's 420 cells carry no field that could express a failure — `protocol.py` refuses a cell whose thirteen fields differ — so every preregistered cell is steady-state, and this document treats a failure as contamination that invalidates a cell everywhere but the one control, whose recovery timing it requires be reported and never judges against anything. The one designed interruption, `interrupt-control-k11`, proves the incomplete-evidence path of the instrument and has no threshold applied to its timing; it belongs to the calibration, wherever that runs. And deployed-failure validation is already owned by [#1362](https://github.com/flink-gcp/flink-connector-gcp/issues/1362), an open on-demand issue under the Tier-3 rig [#38](https://github.com/flink-gcp/flink-connector-gcp/issues/38) rather than under this feature's tree, which takes JobManager and TaskManager replacement in separately observed trials, Operator upgrades, stop-savepoint and rescale, and says of itself that it "is not a new release gate and does not make #1246's feature verdict depend on completing the entire Operator scenario matrix". Recovery correctness — preserved identity, no second physical creation under authorized replay, and expired envelopes stopped before a new send — was settled by [#1245](https://github.com/flink-gcp/flink-connector-gcp/issues/1245) with 56 recovery cases on each supported line. That issue carries one open limit worth repeating here, because the next bullet leans on the same mechanism: its slow test found all twelve identifiers still protected after 105 later attempts each, so the service's actual name-reuse time is unobserved, and neither the configuration readback nor a finite run settles it. #1245 records that as optional calibration rather than a release prerequisite.
- What this assessment still owes about failure is quantitative: **recovery time, and the replay budget a recovery consumes**. The budget it is measured against is `nameRetention - clockSkewAllowance - requestTimeout` from staging, which ADR-0158 sizes at a little under 55 minutes at the product defaults and which is **58 minutes 40 seconds under this assessment's own fixed options** — a one-minute clock-skew allowance rather than five. Not all of it is available: ADR-0158 excludes the part spent before the owning checkpoint completes, up to about one checkpoint interval plus the checkpoint's duration, which at the 60-second intervals of three of the seven shapes is a material share of it. **How that quantity is obtained is not settled here, and a single host cannot settle all of it.** The preregistration records that a JobManager failover *resets* the JobMaster restart budget, so a failover admits a restart sequence a bounded single-host process loss does not. The replacement is the dominant term rather than a negligible one: this run's TaskManager kill recovered in 24.8 seconds, while its two JobManager replacements took 3 min 04 s and 6 min 53 s. Both of those left the TaskManager alive — a surviving writer and committer under a replaced leader, which one JVM holding both roles cannot reproduce. A fourth consumer is not about the host at all: the committer's state is redistributed whole and merged on restore at a parallelism that may change, so a restore into fewer subtasks funnels more envelopes through one commit loop. A rescale produces that on any rig, and exercising it is #1362's, not this refinement's. The instrument is not ready either: the committer's budget snapshot is set inside a commit invocation and cleared in its `finally`, and the restore commit runs in `initializeState` before `open`, so a poller at this run's roughly 19-second cadence can miss it entirely. The reduced assessment does not measure either: #1245 settled recovery correctness, and #1362's deployed evidence is citable for failure behaviour; neither is a precondition for this assessment's verdict.
- The VM rig's evidence contract follows #1327's: local per-run files and a SHA-256 manifest of the frozen inputs, collected to the reviewing host. The GCS receipt reconciliation answers a failure mode a single VM does not have — a Spot Pod vanishing mid-write — so the acceptance items of the [calibration preregistration](evidence/0162-cloudtasks-assessment-1246.md) that name that contract owe a revision for the rig that runs them rather than being carried onto it. The preregistration's revision ([#1448](https://github.com/flink-gcp/flink-connector-gcp/issues/1448)) makes it: the controller's per-file digests and a SHA-256 manifest of the collected tree replace the GCS export, generations and prefix release, and the reconciliation of rows against receipts and terminal counts is kept.
  Each run's receipts and rows are written inside its own run directory, under a `file:` root the controller names rather than the plan: a successor campaign carries its predecessor's arguments into runs with new orders in a new directory, so a root fixed at planning would send every successor run's evidence somewhere else; a plan that names one is refused before any run is claimed, and so is a campaign directory whose path holds anything but letters, digits, `.`, `_`, `-` and `/`, because the probe checks its root with `java.net.URI`, which refuses a space or a `#`, and the root cannot be percent-encoded instead: Flink's `Path` keeps `%20` literal where `java.net.URI` decodes it, on both supported lines. The per-file SHA-256 digests the controller records with each outcome then cover the rows, and they stand in for the exported objects' recorded hashes.
- The rig's controller is split in two. Its core takes each run from the campaign journal, forks one probe JVM for it, heartbeats while it runs, stops it when the reservation counted from its claim runs out, maps its summary line to an outcome, and stops the campaign on an outcome it cannot record; that core is reviewed and tested source in `tools/tier3` (`flink_tier3.vmcampaign`), because a stop rule no test holds is not held. Everything specific to the host is temporary automation kept outside tracked source on ADR-0166's terms, with its source attached to the assessment record: the VM's lifecycle and the classpath's transfer, which are in place before a controller starts, and the per-run work the controller calls through its `prepare` and `settle` hooks — each run's queue, moving its evidence off the host, and Monitoring capture. The measurement runtime it drives stays reviewed source in this repository. The JVM it forks is named by a launcher frozen among the campaign's inputs. The Cloud Tasks image's `target/image-lib/` cannot be that classpath: it copies runtime-scope dependencies only, and the probe, its test-scope dependencies and the `provided` Flink modules are all outside it.
- A run that outlives its reservation is stopped, seen to exit, and recorded `FAILED`; only a run that cannot be made to exit stops the campaign. A probe that had printed its complete summary line when it was stopped keeps that outcome, because it prints first and waits for its threads afterwards, so a JVM that lingers past that point is a slow shutdown rather than a lost measurement; the detail says it did not exit. This departs from ADR-0166's rule, under which a heartbeat that observed an expired worker stopped the campaign — the rule that ended #1327's second attempt at its 427th run, whose readback needed about 310 seconds against a 300-second reservation. There an expired worker was found through the journal and stopped as part of stopping the campaign; here the process that forked the run stops it and waits for it to exit, so the run is not lost, and its cell was spent either way. A reservation that is systematically too short shows as a series of such failures in the journal's failed count rather than as a stop, so the analyzer has to read that detail rather than the count alone.
- The offline analyzer for this rig is `flink_tier3.vmanalyze`, and it contacts nothing. The campaign journal is its ledger of record: a run the journal still calls claimed was lost, even when its directory holds an outcome, and a run whose outcome, detail, command line or file digests disagree with the journal, the plan or the recorded digests is not a measurement. A run that printed its line and then did not exit before its reservation is usable when its evidence passes every other check, and the analyzer lists such runs and every overrun per campaign, because the overrun series rather than the failed count is what shows a reservation that is systematically too short. A repetition is repeated at most once, as `-x2`, and only when the pinned run was lost, failed before observing, outlived its reservation or left incomplete evidence, and only when the repeat was handed out after that run's outcome was recorded or its campaign stopped; a probe counts as failing before observing only when no source start receipt exists, and a restart or a window too short is the job's own behaviour on this host rather than lost evidence, so neither is repeated.
  The observation window is the preregistered one, built from the checkpoint completions the probe records in `checkpoints.jsonl` ([#1473](https://github.com/flink-gcp/flink-connector-gcp/issues/1473)). The analyzer applies the rule in one function and gives a cell without completions no window and no verdict. The report names which acceptance items it applies and which it cannot check on this rig.
- The VM rig's own host calibration is preregistered in the evidence document, on the terms the Decision above sets for any execution host, and its stop conditions are the controller's recorded above.
- The assessment keeps its own resource and cost approval. Its ceiling is USD 20 for the reduced assessment, calibration, operations and host together. Neither the move nor this refinement authorizes a run.

## Consequences

ADR-0158's protocol, correctness tests, scope, deadlines and exclusions remain the implementation contract.
The current at-least-once defaults remain in force, and the staged mode is not made available by this documentation change.
Other connectors keep ADR-0104's gate order.
The original Cloud Tasks measurements and their inconclusive verdict remain archived; the performance decision moves to #1246 rather than being inferred from #1241.

## Alternatives declined

- Require another primitive pass before writing the staged runtime: no material throughput decrease was observed in the capped, sequential cells above, and the final assessment can measure identity and staging costs together against the implemented protocol.
- Reclassify #1241 as passing or conclude that task IDs have no performance cost: its missing repetitions, controls and pacing limitation remain, and the observations cover only the executed conditions.
- Remove performance acceptance from release: the complete mode adds staging, checkpoint, heap and recovery costs that the primitive measurements did not evaluate.
